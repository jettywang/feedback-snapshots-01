# 离线信任图求值原型

判断某个 **(钥匙, UID)** 绑定是否可信。完全离线、有限图：输入只有调用方给定的
钥匙清单、认证签名清单、信任根（含信任量与深度）和阈值。不查询任何全网声誉、
密钥服务器或在线状态——唯一的信任来源是调用方注入的根。

文件：

- `trustgraph.py` — 数据模型 + 求值器 + 路径独立复核
- `demo.py` — 三个小图：普通认证 / 受限转授权 / 环形刷信任
- `test_trustgraph.py` — 21 个针对各条规则的单元测试

## 数据模型

- `Key(fingerprint, controller, revoked, expires)`：`controller` 是调用方断言的
  实际控制者标识，用于把同一控制者的多把钥匙收缩成一个节点。
- `Uid(key, name, revoked)`：UID 撤销登记。
- `Cert(cid, issuer, key, uid, created, expires, revoked, trust_amount,
  trust_depth, trust_regex)`：一份认证签名，**绑定具体的钥匙指纹与 UID 字符串**。
  `trust_amount/depth/regex` 对应 RFC 4880 TrustSignature 子包；三者皆缺省
  （`trust_amount=None`）表示普通认证，只证明绑定、不授予转授权能力。
- `Root(key, amount, depth)`：信任根，注入 `amount` 个信任单位（0–120，
  120=完全信任），允许最多 `depth` 跳转授权。

## 求值规则

设求值时刻为 `now`，目标为 `(K, U)`，阈值为 `T`。

1. **目标自检**：目标钥匙撤销/过期/未知，或 UID 已撤销 → `TARGET_INVALID`，
   不再看图。
2. **认证有效性**：一份认证参与求值，当且仅当：未撤销、`created ≤ now`、
   未过期；签发钥匙在 `now` 未撤销未过期；被认证钥匙未撤销。被丢弃的认证
   连同原因记入 `Verdict.dropped`，供审计。
3. **控制者收缩**：所有钥匙按 `controller` 收缩为节点。同一控制者的多把
   钥匙是同一个节点，它们的认证共享该节点的入流预算，**默认不构成独立
   证明**。调用方只有在有带外证据时才应给两把钥匙不同的 controller 标识。
4. **信任流**：从超级源点向每个根节点 `(controller, depth)` 注入 `amount`
   单位。认证边容量 = `trust_amount`（普通认证为 ∞，即只受上游供给限制）。
   目标流量 = 汇点收到的最大流。
5. **委托深度**：节点按剩余深度分层。沿认证边做*转授权*（到达被认证钥匙
   的节点）要求当前剩余深度 ≥ 1 且该认证 `trust_depth ≥ 1`，到达深度为
   `min(剩余-1, trust_depth-1)`；*终端认证*（直接认证目标 `(K,U)` 的那一跳）
   只要求剩余深度 ≥ 0。普通认证不产生转授权边。
6. **名称范围**：凡带 `trust_regex` 的认证，只有在目标 UID 匹配时才参与
   本次求值（与 RFC 4880 一致：范围约束作用于链条末端的名字）。本原型只
   解释一个安全子集——字面量、`.`、字符类、`* + ? {m,n}`、分组、`|`、
   `^ $`、转义标点，对**整个 UID 串**做大小写敏感的全串匹配；反向引用、
   环视、`\d\w\b` 等一切子集外构造一律视为**无法可靠解释**。
7. **三值结论**：无法解释的认证记为"存疑边"。悲观流（排除存疑边）≥ T →
   `VALID`；乐观流（计入存疑边）< T → `INSUFFICIENT`；两者之间 →
   `UNKNOWN`（不能判断，由调用方决定人工复核或收紧策略）。
8. **环不增殖**：图按深度分层是有向无环结构，且流量守恒——任何节点流出
   不超过流入，唯一源泉是根。环上互签只能搬运已有的信任，不能凭空产生。

## 可核验路径

`VALID` 结论附带把流量分解成的若干条 `根 → 认证 → … → 目标` 路径，每条
标注贡献的信任单位。`Evaluator.verify_paths()` 从原始输入**独立重算**：
逐跳检查认证存在且当前有效、签发者控制者与上一跳衔接、深度预算足够、
范围表达式可解释且匹配目标 UID、路径流量不超过沿途最小容量，且各路径
之和达到阈值。即使求值器本身的流计算有缺陷，伪造的信任也无法通过复核。

## 为什么"有两份有效签名"不一定够

密码学有效 ≠ 身份保证。两份签名都验证通过，仍可能达不到阈值，因为：

- **不独立**：两把签发钥匙属于同一控制者（场景 C3），收缩后只有一份的
  分量——一个实体伪造 N 把钥匙成本极低；
- **量不足**：每份 TrustSignature 的 `trust_amount` 只有 60，合计 120 才够，
  单份或同源的两份都不够（场景 A2 vs A3）；
- **无权转授**：签发者自己没有被授予足够深度，或认证是普通签名、根本
  不含 TrustSignature（场景 B3）；
- **超出范围**：链条上的 TrustSignature 用正则限定了名字范围，目标 UID
  不在范围内（场景 B2）；
- **已失效**：认证或签发钥匙已过期/被撤销（规则 2）；
- **语义不明**：范围表达式超出可解释子集时，结论只能是 `UNKNOWN`，
  不能把它当作支持证据（场景 B4）。

换言之，阈值要求的是**从信任根出发、经授权链传递、彼此独立的信任流量**，
而不是签名的份数。

## 运行

```
cd trustgraph
python3 demo.py                       # 三个场景演示
python3 -m unittest test_trustgraph   # 规则测试
```

## 已知边界（原型取舍）

- 不解析真实 OpenPGP 报文；接入 PGPy 时由适配层把签名子包映射为 `Cert`。
- 控制者归属由调用方断言，原型不做聚类推断。
- 范围表达式语义（全串匹配、大小写敏感）是本原型的固定选择；真实部署
  若采用其他语义，应把相应表达式按"无法解释"处理或另行形式化。
- 信任量按容量模型求最大流，不模拟 GnuPG trustdb 的具体迭代细节。
