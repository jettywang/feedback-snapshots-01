# 排查报告：区域 authority 与独立 OIDC authority 的归属判定

- 仓库：MSAL Python `1.39.0`（基线提交 `173711c`，工作区未改动 `msal/` 任何代码）
- 实验：`investigation/experiment_regional_vs_oidc.py`（全程离线、内存假 HTTP 传输，所有目的地均为 RFC 2606 保留的虚构 `.example` 名称）
- 原始证据：`investigation/transcript.txt`、`investigation/evidence.json`
- 复现：`.venv/bin/python investigation/experiment_regional_vs_oidc.py`（退出码 0 表示全部断言成立）

## 1. 结论先行

1. 这版代码里**不存在**“区域令牌请求失败后自动改打中央 authority”的运行时回退。客户端在构造时就静态选定：`client = self._regional_client or self.client`（`msal/application.py:2688`）。区域客户端存在时，令牌 POST 永远优先走区域；区域请求报错不会在 `acquire_token_for_client()` 内部静默切换到中央。
2. 因此日志里“从另一个 authority 完成”只有三类代码内来源：
   - **预期的区域派生主机**：由配置主机名 + 已校验的 region 字符串在本地拼出（`msal/application.py:899` 至 `msal/application.py:914`），不来自任何发现记录；
   - **发现记录里的 URL**：实例发现返回的 `tenant_discovery_endpoint`（`msal/authority.py:176`）或 OIDC 文档里的 `token_endpoint`（`msal/authority.py:117`），MSAL **原样采用，不做同主机绑定**；
   - **另一个进程/另一份配置/环境变量**（`MSAL_FORCE_REGION`、`REGION_NAME`），聚合日志时需要先排除。
3. 足以确定“发现服务对端是谁”的事实组合在**配置派生层 + TLS 层**：配置层在发包前就知道期望主机名，TLS（默认校验证书与主机名）验证对端确实是该名字。发现文档里的 `issuer`/`token_endpoint` 只是声明，Entra 路径对 `issuer` **存而不验**（`msal/authority.py:115`，校验门仅 OIDC 配置触发，`msal/authority.py:122`），文档层本身不足以证明归属。
4. 单独配置 `oidc_authority` 时多一道 `has_valid_issuer()` 门（`msal/authority.py:203` 至 `msal/authority.py:258`），外观相近但无法绑定的 issuer 会在构造期被拒（时间线二，T2/T2b）。但这只是“字符串相容”判定，不是对端认证，也**不校验 `token_endpoint`**；并且这道门**不覆盖** OIDC 应用叠加 region 后派生出的区域 Authority（交叉项 X1）。
5. 两条时间线的实测要点：
   - 时间线一（T1）：获准的区域发现返回 200 但缺少 `token_endpoint` → 构造应用时直接 `KeyError: 'token_endpoint'`，实际只发出 2 个发现 GET，**没有任何令牌 POST**。这是“配置/服务不完整”，应退回配置后重新采集，而不是猜归属。
   - 时间线二（T2/T2b）：OIDC 文档的 issuer 是后缀仿冒名或缺失 → `ValueError: The issuer ... does not match the authority ... or a known pattern`，只发出 1 个发现 GET，**没有令牌 POST**。这是“记录无法支持 issuer 结论”，应停止并核查来源。

## 2. 两条调用路径逐步核对

### 2.1 Entra authority + `azure_region`

装配顺序（`msal/application.py:734` 至 `msal/application.py:771`）：

1. `authority` 与 `oidc_authority` 互斥（`msal/application.py:734`）。构造中央 `Authority`。
2. 主机是已知 Entra 主机（清单 `WELL_KNOWN_AUTHORITY_HOSTS`，`msal/authority.py:19` 至 `msal/authority.py:33`）时，**不发实例发现请求**，直接在本地拼 `https://<host>/<tenant>/v2.0/.well-known/openid-configuration`（分支条件 `msal/authority.py:161` 至 `msal/authority.py:184`）。
3. 主机未知且默认 `validate_authority=True` 时，向固定的实例发现端点查询：非已知主机一律用 `https://login.microsoftonline.com/common/discovery/instance`（`msal/authority.py:45` 至 `msal/authority.py:51`、`msal/authority.py:163` 至 `msal/authority.py:167`），实际查询参数为 `authorization_endpoint=<拼出的 authorize URL>&api-version=1.0`（`msal/authority.py:283` 至 `msal/authority.py:288`）。返回 `invalid_instance` → 明确 ValueError（`msal/authority.py:168` 至 `msal/authority.py:175`）；否则**原样**取 `payload['tenant_discovery_endpoint']` 作为下一个 GET（`msal/authority.py:176`，缺键即 `KeyError`）。
4. 拉取 OIDC 文档（`msal/authority.py:290` 至 `msal/authority.py:306`）：4xx 抛含该发现 URL 与响应体的 `ValueError("OIDC Discovery failed on ...")`，再被包成 “Unable to get authority configuration for ...”（`msal/authority.py:97` 至 `msal/authority.py:114`）；5xx/网络错误走 `raise_for_status()`。
5. 读取文档：`issuer` 仅保存（`msal/authority.py:115`），`authorization_endpoint`、`token_endpoint` 直接按键取用（`msal/authority.py:116` 至 `msal/authority.py:119`）。**Entra 路径没有任何 issuer 复核，也不检查 token_endpoint 主机是否等于 authority 主机。**
6. 构造客户端时若有 `client_credential`，调用 `_get_regional_authority()`（`msal/application.py:1016` 至 `msal/application.py:1018`）：
   - region 必须是单个小写 DNS label，正则 `^[a-z](?:[a-z0-9-]{0,61}[a-z0-9])?$`（`msal/region.py:8`，显式配置非法直接 ValueError，`msal/application.py:38` 至 `msal/application.py:44`；`westus2.login.microsoft.com` 这类带点值会被拒绝，见 `tests/test_application.py:161` 至 `tests/test_application.py:166`）。
   - 区域主机名是**纯本地派生**：四个经典主机（`login.microsoftonline.com`、`login.microsoft.com`、`login.windows.net`、`sts.windows.net`）→ `<region>.login.microsoft.com`；其他配置主机 → `<region>.<central.instance>`（`msal/application.py:900` 至 `msal/application.py:909`）。
   - 区域 `Authority` 以 `instance_discovery=False` 构造（`msal/application.py:910` 至 `msal/application.py:914`），因此发现 URL 同样是本地拼出的 `/<tenant>/v2.0/.well-known/openid-configuration`，再走第 4、5 步——**包括“issuer 存而不验、token_endpoint 原样采用”**。
   - region 来源：`azure_region="x"` 显式值；`azure_region=True` 才采用自动检测值；`azure_region=None` 时只有 `MSAL_FORCE_REGION` 能把配置值改成字符串（`msal/application.py:880` 至 `msal/application.py:894`）。注意 `REGION_NAME` 在 `None` 下仍会被读入“检测值”、可能打出 mismatch 警告，但 `region_to_use` 取的是配置值 `None`，即不启用区域客户端。检测本身先读 `REGION_NAME`，否则访问链路本地 IMDS `http://169.254.169.254/metadata/instance/compute?api-version=2021-02-01`（`msal/region.py:27` 至 `msal/region.py:43`）。配置值与检测值不一致会打 WARNING（`msal/application.py:887` 至 `msal/application.py:890`）。
7. 令牌发送：客户端凭证流程 `client = self._regional_client or self.client`（`msal/application.py:2688`），POST 到 `configuration["token_endpoint"]`（`msal/oauth2cli/oauth2.py:288` 至 `msal/oauth2cli/oauth2.py:293`）。密钥型凭证在请求体里带 `client_secret`（实验实测）；证书型凭证生成的 assertion 的 `audience=authority.token_endpoint`（`msal/application.py:990` 至 `msal/application.py:994`）。
8. 两个容易误判的取证点：
   - 区域令牌写入缓存时 `environment` 仍记**中央** `authority.instance`（`msal/application.py:1034` 至 `msal/application.py:1035`），所以查令牌缓存看不出真实区域目的地。
   - 唯一的内置网络容错是构造中央 `Authority` 抛 `OSError` 且主机属于已知 Entra 主机、且配置了 region/force region 时，用 `instance_discovery=False` 重试一次（`msal/application.py:748` 至 `msal/application.py:764`；测试 `tests/test_application.py:141` 至 `tests/test_application.py:159`）。对已知主机而言两次 URL 相同，不是“换到另一个 authority”。

实验 R0 实测的正常序列（虚构主机 `login.tailwind-demo.example` + `region-a`）：

```
GET  https://login.tailwind-demo.example/tenant-7777/v2.0/.well-known/openid-configuration
GET  https://region-a.login.tailwind-demo.example/tenant-7777/v2.0/.well-known/openid-configuration
POST https://region-a.login.tailwind-demo.example/tenant-7777/oauth2/v2.0/token
```

### 2.2 单独配置 `oidc_authority`

1. 不允许同时给 `authority` 与 `oidc_authority`（`msal/application.py:734` 至 `msal/application.py:735`）。OIDC 初始化直接把输入 URL 规范化并拼 `/.well-known/openid-configuration`（`msal/authority.py:131` 至 `msal/authority.py:138`），**没有实例发现环节**。
2. 拉文档、取端点同上；随后立即执行 issuer 门（`msal/authority.py:121` 至 `msal/authority.py:130`）。判定规则（`msal/authority.py:203` 至 `msal/authority.py:258`）：
   - issuer 与 `oidc_authority` 完全相同（忽略尾部 `/`）；
   - issuer 主机属于 `WELL_KNOWN_AUTHORITY_HOSTS`（注意：**任意** OIDC 主机提供的文档只要声明这种 issuer 也通过——它是清单规则，不证明文档来自微软）；
   - issuer 是已知主机的单标签区域前缀（如 `westus2.login.microsoft.com` → 基域 `login.microsoft.com`）；
   - 或剥掉首个标签后等于配置主机（如 `region-a.id.tailwind-demo.example` 对 `id.tailwind-demo.example`，规则 3b）；
   - 或 scheme+netloc 与配置完全相同（路径可不同）；
   - 或 issuer 是已知 B2C/CIAM 主机的子域。
   - 都不满足（含 issuer 缺失）→ 构造期 ValueError，应用对象不会诞生，更不会发令牌 POST。
3. 通过后，`token_endpoint` 仍按文档原样使用，**没有任何规则核对它的主机**（`msal/authority.py:117`）。实验 O0 中同主机文档的序列为：

```
GET  https://id.tailwind-demo.example/tenant-9/.well-known/openid-configuration
POST https://id.tailwind-demo.example/tenant-9/oauth2/token
```

4. 另一道“issuer”不要混淆：ID Token 的 `iss` 签名/声明校验在当前令牌获取流程中**默认不做**，`decode_id_token()` 已标注弃用且不再被获取流程调用（`msal/oauth2cli/oidc.py:95` 至 `msal/oauth2cli/oidc.py:114`、`msal/oauth2cli/oidc.py:192` 至 `msal/oauth2cli/oidc.py:202`）。如果业务依赖 ID Token 声明，需要应用自行校验。

### 2.3 交叉项：`oidc_authority` 与 region 同时存在（实验 X1）

`oidc_authority` 并不关闭区域客户端构造。只要给了客户端凭证且 region 生效，MSAL 会用**Entra 初始化逻辑**（不带 `oidc_authority_url`）再建一个区域 `Authority`，因此：

- 主 OIDC 文档过了 `has_valid_issuer()`；
- 区域派生文档（`https://<region>.<oidc-host>/<tenant>/v2.0/.well-known/openid-configuration`）的 issuer **不受任何校验**；
- 令牌时刻 `self._regional_client` 优先，POST 到区域文档指定的任意 `token_endpoint`。

X1 实测：区域文档声明了无法归属的 issuer 和站外 token 地址，MSAL 照常带着 `client_secret` POST 成功。若配置口径是“单独配置 OIDC authority”，应显式 `azure_region=False` 并清除 `MSAL_FORCE_REGION`，避免这条交叉路径。

## 3. 哪一层知道的事实足以确定对方身份

| 层 | Entra 区域路径知道的事实 | OIDC authority 路径知道的事实 | 能否据此确定对端身份 |
|---|---|---|---|
| 配置/本地派生层 | 原始 authority 主机、已校验的单标签 region、按固定规则算出的唯一区域主机；发现 URL 本地拼出 | `oidc_authority` 主机；发现 URL 本地拼出 | 只给出“期望名字”，不认证对端；但它是后续比对的基准 |
| 实例发现层（仅未知 Entra 主机默认触发） | 固定查询 `login.microsoftonline.com/common/discovery/instance`（或显式覆盖端点）；收到 `tenant_discovery_endpoint` 原样跟随 | 不经过 | 只有在 TLS 验证了固定发现端点时，该指引才可归因于它；字符串本身不证明任何事（实验 ID1–ID3） |
| OIDC 发现文档层 | `issuer`（存而不验）、`token_endpoint`（原样采用，无同主机约束） | 同样的文档，且构造期跑 `has_valid_issuer()` | Entra：**不足**（T1b 证明文档可把带密钥 POST 引向站外）。OIDC：issuer 层足以**拒绝无法绑定的记录**（T2），但“通过”只是字符串相容，且不管 token_endpoint |
| issuer 判定层 | 不存在 | 同时持有配置 URL、文档 issuer、已知主机/后缀规则 | 足以做出“该记录是否支持 issuer 结论”的判定；不是密码学认证，也不覆盖区域派生文档（X1） |
| TLS/传输层 | 默认 `verify=True`，urllib3/certifi 校验证书链与主机名；自定义 `http_client` 需自行保证 | 同左 | **真正把 TCP 对端绑定到“期望主机名”的层**。配置名 + TLS 验证通过，二者合起来才足以确定发现服务对端身份 |
| 令牌发送层 | POST 到文档 token_endpoint；携带 secret 或以其为 audience 的 assertion | 同左 | 目标可能与发现主机不同；归属必须靠出站目的地核对/TLS，MSAL 不再二次把关 |

一句话：**“应该联系谁”在配置派生层就已完全确定；“实际和谁通信”靠 TLS 层证明；发现文档的 issuer 字段在 Entra 路径上不提供身份结论，在 OIDC 路径上提供一道可失败关闭的字符串佐证。**

## 4. 两条可重复时间线

实验用内存路由表精确控制“发现文档/本地输入”，并记录每一个实际查询与尝试发送的目的地（GET 含 query，POST 只记录键名与“密钥存在”，不记录密钥值）。

### 时间线一：获准的区域发现不完整（T1，含正常基线 R0 与分支 T1b）

配置（全部虚构）：`authority=https://login.tailwind-demo.example/tenant-7777`、`azure_region="region-a"`、`instance_discovery=False`、`REGION_NAME=region-a`（消除 IMDS 旁查询）。

| 步骤 | 实际查询/目的地 | 代码行为与反馈 |
|---|---|---|
| 1 | `GET https://login.tailwind-demo.example/tenant-7777/v2.0/.well-known/openid-configuration` | 中央发现成功 |
| 2 | `GET https://region-a.login.tailwind-demo.example/tenant-7777/v2.0/.well-known/openid-configuration` | 区域主机由本地规则 `<region>.<配置主机>` 派生；返回 200 但文档缺少 `token_endpoint` |
| 3 | 无 POST | `msal.ConfidentialClientApplication(...)` 直接抛出 `KeyError: 'token_endpoint'`（`msal/authority.py:117`），区域客户端未建成 |

相邻实测事实：

- 若字段是 `null`，`canonicalize(None)` 抛 `ValueError: Your given address (None) should consist of an https url ...`（`msal/authority.py:119`、`msal/authority.py:275` 至 `msal/authority.py:281`）。
- 若区域发现返回 4xx（实验 F1），得到可读反馈：外层 `ValueError: Unable to get authority configuration for https://region-a.login.tailwind-demo.example/tenant-7777 ...`，异常链 `__context__` 里是 `OIDC Discovery failed on https://region-a.login.tailwind-demo.example/tenant-7777/v2.0/.well-known/openid-configuration. HTTP status: 400, Error: ...`（对应 `msal/authority.py:97` 至 `msal/authority.py:114`、`msal/authority.py:295` 至 `msal/authority.py:302`）。注意外层消息会点名区域 authority，是最好的日志取证字段。
- 发现成功但令牌端点拒绝时（实验 F2，400 + `invalid_client`），MSAL **不抛异常**，而是把 `{"error": ..., "error_description": ...}` 作为 `acquire_token_for_client()` 的返回字典；失败 POST 的目的地仍是区域 `token_endpoint`。只有 5xx 才会在 HTTP 层 `raise_for_status()`（`msal/oauth2cli/oauth2.py:294` 至 `msal/oauth2cli/oauth2.py:300`），网络异常在无缓存令牌时向上抛（`msal/application.py:1833` 至 `msal/application.py:1837`）。所以“日志里有 error 返回但流程走到了某主机”与“构造期直接失败”是两类不同证据。
- 分支 T1b：文档完整但把 `token_endpoint` 改成 `https://token.delegate-demo.example/v9/token` 时，实测第 3 步为 `POST https://token.delegate-demo.example/v9/token`，请求体含 `client_secret`，MSAL 无任何异议。
- 实例发现变体 ID1–ID3：实际查询 `GET https://discovery.tailwind-demo.example/common/discovery/instance?api-version=1.0&authorization_endpoint=https%3A%2F%2Flogin.tailwind-demo.example%2F...%2Foauth2%2Fv2.0%2Fauthorize`；返回的 `tenant_discovery_endpoint` 被逐字跟随到 `discovered.tailwind-demo.example`，最终 token 主机也随之改变；`invalid_instance` 给明确回退提示；缺 `tenant_discovery_endpoint` 键则 `KeyError`。

这条时间线支持的判定：区域主机名本身符合本地派生规则，所以“去区域 authority 完成”是预期形态；但发现记录不完整意味着**这一次没有形成可用的归属证据链，也没有发出令牌**。应退回配置（恢复上一个 region/中央 authority）并重新采集完整文档与目的地，而不是根据半句“from another authority”放行。

### 时间线二：外观相近、无法支持 issuer 结论的发现记录（T2/T2b）

配置（全部虚构）：`oidc_authority=https://id.tailwind-demo.example/tenant-9`，环境中清除 `MSAL_FORCE_REGION`/`REGION_NAME`，不传 `azure_region`。

伪造发现文档地址（本地拼出）：
`GET https://id.tailwind-demo.example/tenant-9/.well-known/openid-configuration`

- T2 记录：`issuer=https://id.tailwind-demo.example.lookalike.example/tenant-9/v2.0`。它把受信任的配置主机名当作自己的前缀标签，肉眼“外观相近”，但剥掉首个标签得到 `tailwind-demo.example.lookalike.example`，既不等于配置主机 `id.tailwind-demo.example`，也不在已知主机清单；netloc 不同，也不是 B2C 后缀。判定 False → 构造期 ValueError，实测只有上述 1 个 GET，无 POST。
- T2b 记录：没有 `issuer`（JSON `null`）。`has_valid_issuer()` 第 214 至 215 行直接 False → 同样 ValueError（消息里打印 `issuer 'None'`），只有 1 个 GET，无 POST。
- 对照“相近但可支持”的记录：`issuer=https://region-a.id.tailwind-demo.example/tenant-9/v2.0` 经规则 3b 通过；同主机不同路径经规则 4 通过；完全一致经规则 1 通过（TRUTH 段实测）。

报错原文（截断）：`The issuer '...' does not match the authority 'https://id.tailwind-demo.example/tenant-9' or a known pattern. When using the 'oidc_authority' parameter ...`（`msal/authority.py:123` 至 `msal/authority.py:130`）。

这条时间线支持的判定：**应用自身的 issuer 层已经给出“无法证明归属”的决定性证据并失败关闭**。如果真实日志里出现的是这条 ValueError，而令牌却仍然发往了某个仿冒主机，那说明运行的不是这版代码/不是这条配置路径（例如走了 2.3 的区域交叉路径、自定义 http_client、或日志来自其他进程），应停止并核对部署物。

## 5. 对照两份真实 MSAL 日志的取证程序

这版仓库没有 “completed from another authority” 字样的日志语句；可核对的硬事实是目的地 URL 与几条固定日志：

1. 找启动/构造期日志：`Region to be used: '...'`（DEBUG，`msal/application.py:898`）与 `Region configured (...) != region detected (...)`（WARNING，`msal/application.py:889`）。先确认进程实际生效的 region 及来源（参数 / `MSAL_FORCE_REGION` / `REGION_NAME` / IMDS）。
2. 取 HTTP 目的地，三选一：
   - 开 DEBUG：`logging.basicConfig(level=logging.DEBUG)`，urllib3 会打印 `Starting new HTTPS connection (1): <host>:443` 与 `"POST /<path> HTTP/1.1"`；msal 打印 region 决策。注意异常日志 `Token response is not in json format: %s` 可能打印响应体（`msal/oauth2cli/oauth2.py:301` 至 `msal/oauth2cli/oauth2.py:304`），共享日志前需脱敏。
   - 包一层记录型 `http_client`（最安全，可只记 method/host/path，对 body 键名与密钥打码），模板就是本实验的 `RecordingTransport`。
   - 用出口代理/网络流日志核对 SNI、CONNECT 与 POST 主机。
3. 把每个目的地与第 6 节的允许集合逐项比对，并核对异常文本：`Unable to get authority configuration for https://<host>/...`、`OIDC Discovery failed on <url>`、`does not match the authority ... or a known pattern`、`invalid_instance`。
4. 不要用令牌缓存里的 `environment` 字段反推区域目的地——它被刻意写成中央实例（`msal/application.py:1034` 至 `msal/application.py:1035`）。
5. 对外分享证据时，参照本报告把真实租户/主机替换成虚构名（如 `*.tailwind-demo.example`）；本仓库内的实验已全部使用虚构地址，不产生任何真实查询。

### 5.1 两份“from another authority”日志的判读画像

| 日志/证据画像 | 对应实验 | 判定 |
|---|---|---|
| DEBUG 有 `Region to be used: '<合法单 label region>'`；urllib3/传输记录显示先 GET 中央发现、再 GET/POST `<region>.login.microsoft.com`（经典主机）或 `<region>.<配置主机>`；无 issuer 报错；TLS 正常 | R0 | **继续**：这是设计内的区域 authority，不是被发现结果带走；本版不存在区域失败后自动回中央，所以“在区域主机完成”本身就是正常终态 |

## 6. 继续 / 退回配置 / 停止的条件

**继续（判定为正常区域 authority）——需同时满足：**

- 日志中的主机等于本地派生值：经典四主机 → `<region>.login.microsoft.com`；自定义主机 → `<region>.<配置主机>`；region 是无点的合法单 DNS label。
- 发现路径是本地拼出的 `/<tenant>/v2.0/.well-known/openid-configuration`；若经过实例发现，`tenant_discovery_endpoint` 来自固定的 `login.microsoftonline.com` 发现端点且其主机属于你批准的云/主机集合。
- TLS 校验开启且成功（未设 `verify=False`，自定义 `http_client` 未关闭主机名校验，CA 信任库未被改动）。
- 没有未解释的 region 配置/检测不一致 WARNING；生效 region 与变更单一致。
- OIDC 配置若叠加了 region，已单独验证区域派生文档及其 token_endpoint（因为 issuer 门不覆盖它，见 X1）；否则应 `azure_region=False` 并清除 `MSAL_FORCE_REGION`。
- token POST 主机与区域发现主机同源，或属于明确书面批准的委托 token 主机。

**退回配置（证据不完整/有歧义，先恢复上个已知良好配置再采一轮）：**

- 时间线一各类：区域发现 200 但缺字段（`KeyError: 'token_endpoint'`、`None` 端点 ValueError）、发现端点 4xx/5xx、`OSError` 网络失败、实例发现载荷缺 `tenant_discovery_endpoint`。
- 出现 `Region configured (...) != region detected (...)`、非法 region 被丢弃的 WARNING，或无法说明 `MSAL_FORCE_REGION`/`REGION_NAME` 来源。
- 只有“from another authority”这类转述，拿不到第 5 节的目的地级证据。
- 动作：`azure_region` 恢复为变更前值；要彻底排除区域行为用 `azure_region=False`（`msal/application.py:878` 至 `msal/application.py:879`），同时清理环境变量；`oidc_authority`/`authority` 恢复上个已知良好值后重启进程（环境变量只在构造期读取）。这版没有区域失败后的自动中央回退，不要把“再试一次可能回中央”当作机制依赖。

**停止（归属无法证明或疑似被引导至仿冒方）：**

- 出现 T2/T2b 的 issuer 不匹配 ValueError，或任何 `has_valid_issuer()` 为 False 的记录；不得通过关闭校验/改代码绕过。
- 实际 POST 主机落在派生名/批准集合之外，尤其是发现文档指定的站外 `token_endpoint`（T1b、X1），或 `<可信名>.lookalike.example`、连字符仿冒等后缀/拼写近似主机。
- 已观察到向上述外部主机发送请求——因 `client_secret` 在请求体中、证书 assertion 以该 token URL 为 audience，应按凭证泄露处理：立即轮换 secret/证书，并核查出口与 DNS/TLS。
- `invalid_instance` 指向你未登记的主机；出现 TLS 证书/主机名校验错误、`verify=False`、未知 CA 或自定义 `http_client`。
- 同一时间窗内不同进程目的地不一致且无法用配置/环境变量解释：先冻结发布、保留 DEBUG 日志与内存型传输记录，再比对部署版本是否确为 `173711c`/1.39.0。
